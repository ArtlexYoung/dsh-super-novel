# P0 真实模型小规模对照

日期：2026-09-20。结论：真实 Harness → 模型 → 输出/事件/用量通路已验证；这三个样本不足以证明写作质量提升。当前候选消耗更多 token，不能宣传节省成本或完整小说流程已经通过评测。

## 方法与版本

参考 dsh-super-code 的 `eval/adapters/harness-super-code.mjs`、`eval/runners/dsh-runtime-smoke.mjs` 和请求用量记录方法：真实创建 Agent、挂载 preset、保留每次尝试、同一任务配对、先检查 provider。没有执行它的 SWE-bench 或照搬编程评分门槛。

- 插件：`0.1.0-alpha.1`，产品代码基线 `d3d4af7`；Harness：`c291e7961a` / `0.1.5-rc.2`；macOS arm64，Node.js `24.18.1`。
- 模型：TokenHub `deepseek-v4.1-flash`，端点 `https://tokenhub.tencentmaas.com/plan/v3`；凭证仅从 `DSH_MODEL_API_KEY` 读取。
- 两组 `reasoningEffort=high`、`maxTokens=6000`、每次超时 180 秒、无自动重试、temperature 沿用 provider 默认。不同于 super-code 历史不限输出的协议，这里限制单次输出预算。
- 对照为普通小说助手提示词，候选真实挂载 `dsh-super-novel`，同用 Harness 核心运行时和身份提示，无工具。**不是**内置 standard/minimal 与完整产品的发布评测。
- 首章、约束续写、局部润色三个合成样本，每组每题一次，任务顺序交替；同一素材、独立会话。无真实小说材料、文件读取、shell 或委派调用。
- 调用前冻结完整素材、顺序、参数、提示词/组合文件/runner 哈希。未进行针对输出的提示词修改、重采样或挑选最佳结果。

冻结协议与原始材料：本地 `eval/live-p0-l2/manifest.json`、`cases.json`；逐项 `*.context.json`、`*.events.json`、`*.result.json`、`*.txt`；汇总 `summary.json` / `aggregate.json`。整个 `/eval/` 被 Git 忽略，不随代码或 npm 包发布。

## 观测结果

| 样本 | 普通助手 total tokens | 写作预设 total tokens | 普通助手耗时 | 写作预设耗时 |
| --- | ---: | ---: | ---: | ---: |
| 首章 | 5,078 | 5,669 | 20.513 秒 | 23.085 秒 |
| 连续性续写 | 4,297 | 4,127 | 24.053 秒 | 19.048 秒 |
| 局部润色 | 1,498 | 2,464 | 6.022 秒 | 9.652 秒 |
| 合计 | 10,873 | 12,260 | 50.588 秒 | 51.785 秒 |

候选 total tokens 增加 12.76%，总耗时增加 2.37%。耗时是本机 Agent 创建至事件保存前后的 wall time，包含网络与宿主开销；不是纯解码时间，三次样本无法推断稳定速度差异。

6 次任务均以 `completed` 结束，每次一个已结算请求，0 次重试、0 次工具调用。逐项 `request/header` 确认相同 provider/model/high/6000。候选上下文包含真实写作提示词，对照上下文包含普通助手提示词；无小说存储或审校功能参与。

采用宿主报告的 `totalTokens`，不把 cache 重复加到它上面。部分 `cacheReadTokens`、reasoning tokens、cache write tokens 未报告，保持未知；output tokens 不等同于正文长度。费用没有账单或价格证据，不能计算金额。

## 检查与文本审阅

机械检查全部通过：首章分别 717 / 855 个汉字，续写 563 / 638；禁用短语未出现、秘密身份关键词未泄露。润色首尾文字精确保留，都是三段，中段分别 115 / 106 个汉字（要求 100–180）。这些检查不等于文学评分，也不能凭关键词缺失证明没有隐含泄密。

以下是本轮执行者对完整文本的定性审阅，**不是双人盲评**：

- **首章**：两组均保留修表换母亲来信的动机、主人公限知视角与声音来源悬念。候选把包表、撒谎、递当票遮挡等动作连成对巡夜人的应对，但末尾连续添加“信被烧了”“火场名单”等新悬念，后续需要兑现，不能仅以悬念数量判断更好。
- **续写**：两组均保持断腕、不会游泳、药包不进水、尚在河上、未出现援兵等主要约束。候选让沈砚交出夹板，受伤后果延续；普通助手临时赋予药包“三截老山参”，形成付款资源。前者补船缝的交换价值铺垫较少，后者新增贵重药材可能削弱“资源不足”的压力，应由作者判断是否接受。
- **共同因果弱点**：两组都让船夫以“多一人船吃水”为由拒载，收下额外物品后直接允许两人上船。若此前是在索价而非真的承载不足，需要给读者可见证据；候选补船缝也没有充分解释为何能解决载重。这是待审校的说服力问题，不能用字数/禁词检查发现。
- **润色**：两组均保留三把钥匙、未上锁/未打开的木箱和最终带箱不带钥匙。动作比原稿具体，但“肩膀塌下去”“喉结动了动”仍偏常见，尚无充分证据说明候选的人物声音更有辨识度。

下一步将上述因果弱点作为独立审校的回归素材；P1/P2 实现工作台与持久化后，再按 P3/P4 接入事实与审校。P5 仍需更多题材、跨章链路、重复采样、同预算对照及多名评阅者，不能把本轮 6 次完成率当作质量提升率。

## 失败尝试与用量边界

第一次实验 `eval/live-p0-l1`：健康检查通过（48 tokens）；首个普通助手请求后，runner 沿用了旧版 `session.events`，在保存阶段失败。其任务输出、用量未成功保留，不能认为没有模型消耗，也没有把它混入正式配对。

修正版 `live-p0-l2` 使用当前 `snapshotEvents()`，另一次健康检查用量 55 tokens，然后完成上述 6 次任务。已知总量为 **23,236 tokens**（23,133 个配对任务 tokens + 103 个健康检查 tokens），还要加上首次采集失败调用的未知用量。没有隐藏这次失败，也没有对失败的输出作质量判断。

## 重现

先按 README 构建和链接 Harness。将三个合成案例放入新的、被忽略的 `eval/<run>/cases.json`，每项包含唯一小写 `id`、`prompt`、`minHan`、`maxHan`，可选 `forbidden`、`prefix`、`suffix`、`review`。素材与领域检查项需要在执行前明确，不能将私人稿件作为默认测试材料。

```sh
node scripts/live-eval.mjs prepare eval/<run>
node scripts/live-eval.mjs run eval/<run>
```

`prepare` 不调用模型。`run` 会真实计费调用 provider，需要已设置密钥环境变量；不要将密钥写进命令、文件或提交。manifest 检测参数/源码漂移；已有 run-started 文件会拒绝再次执行，避免误重跑。每次会话独立、运行失败停止后续样本。原始文本仅在本地 eval 中保存，版本库只保留 runner、统计测试和此摘要。
